# neolith-rs: Rust UI Rebuild Design

*Status: proposal, 2026-11-11. Companion to [`../SPEC.md`](../SPEC.md), which describes the current Django/Leaflet app and numbers its defects (§9, cited here as "D1"–"D27").*

## 1. Goals and non-goals

**Goals**
- Rebuild the browser UI (map, clock, settlements, editor) in Rust, with the **web (WASM)** and **native desktop** apps built from one codebase.
- Draw the world as a **3D game board**: a bounded slice of a sphere, solid and slightly stylized, so Earth's curvature is visible. No full globe. Tiles can be raised to their elevation (the relief layer). It can morph smoothly to a flat board for precise editing.
- Fix the playback and editor defects by design, not with patches (D1–D13).
- Keep a headless, tested core crate that the future simulation (cultures, tech, DNA) can build on.
- Make the Django backend optional. Everything it does today (load the data, diff epochs, compute adjacency) is cheap enough to do on the client.

**Non-goals (for now)**
- Gameplay, simulation and AI. The core crate leaves room for them but doesn't build them.
- Base map tiles. The current app has none, and the hexes *are* the map.
- Re-running the QGIS pipeline. We consume `combined_map.geojson` as it is.

## 2. Key findings that shape the design

These were checked against the data on 2026-11-11:

1. **The hex grid is a perfect rectangle.** It has 190 columns and about 139 rows of flat-topped hexes. Width is 0.57735° and height 0.5° (lon/lat), columns are `0.75·width` apart, and fractional-column error is about 1e-13. Ids run 1 to 26,410 with no gaps. So:
   - Geometry doesn't need storing. Every polygon comes from `(col, row)`.
   - Adjacency is grid arithmetic, not a 1 MB lookup map.
   - Hit-testing is O(1): turn the cursor into lon/lat, then into hex coordinates.
2. **`climate` is a pure function of `koeppen`** (a 1:1 mapping across all hex-epochs), so we store one field, not two.
3. **Epochs are few and fixed** (8 keyframes from −10000 to −3000). The whole time-varying state is about 26k × 8 × 3 bytes, roughly **0.6 MB uncompressed**, compared with 27.7 MB of GeoJSON.
4. Leaflet's cost came from one SVG layer per hex (about 26k DOM nodes, D3, D4). A GPU mesh with one colour per hex removes that whole class of problem.
5. **The grid covers enough of the planet for curvature to show.** It spans 82° of longitude and 70° of latitude (6°N to 76°N), about a ninth of the sphere. Because the hexes are defined in lon/lat, each one shrinks to about cos(75°) ≈ 0.26 of its equatorial width near the top. A flat Mercator map hides this. The curved board shows it as it really is (see §11 on a future equal-area grid). Because the grid is a 190 × 139 rectangle in (col, row), the board's outline is a curved "rectangle" with jagged hex edges, which gives a natural game-board shape.
6. **The hexes are small enough to draw as flat triangles.** A 0.58° edge bows out from its straight chord by about 1.3×10⁻⁵ of Earth's radius, which is invisible. So curvature comes entirely from where the vertices sit, with no subdivision needed. At the closest zoom the hexes are about 0.01 units on a unit sphere, well within `f32` precision.

## 3. Framework choice

| Option | Fit | Verdict |
|---|---|---|
| **eframe/egui + a custom wgpu board renderer** | Immediate-mode UI is a natural fit for panels, palettes, inspectors, undo/redo and sliders. The 3D scene is just *one static mesh* (the board) plus a few overlays, so it needs about 600 lines of our own wgpu code: one pipeline, one shader, an orbit camera and analytic picking. It builds for both web and native, compiles fast and has few dependencies. | **Recommended** |
| Bevy (+ bevy_egui) | Comes with 3D, cameras, lighting and picking. But most of that is wasted on a single sphere mesh, the WASM bundle is much bigger, builds are slower and the API changes often. Editor UI still has to go through egui. | Revisit when the simulation needs ECS. The core crate stays engine-agnostic so the switch is cheap. |
| Leptos/Yew/Dioxus + Leaflet via JS interop | Keeps the DOM, so it keeps the Leaflet performance problem. Mostly a rewrite of glue code. | Rejected |
| Tauri around the existing JS | Not really a rebuild. | Rejected |

## 4. Workspace layout

```
neolith-rs/
  Cargo.toml              # workspace
  crates/
    core/                 # no UI deps. Data model, time, grid, edits. 100% unit-tested.
    convert/              # CLI: combined_map.geojson + settlements.geojson → world.bin (and back)
    app/                  # eframe app: map widget, panels, clock, editor tools
  assets/
    world.bin             # generated by `convert`, checked in (~200 KB compressed)
  index.html, Trunk.toml  # web build via trunk
```

`core` is the boundary that matters. `app` turns user input into `core` commands and turns `core` state into pixels. A future `sim` crate depends only on `core`.

## 5. Core data model (`crates/core`)

```rust
/// Signed astronomical-ish year: negative = BCE. One type everywhere, formatted only at the UI edge.
pub struct Year(pub i32);                      // Display: "7500 BCE" / "200 CE"

pub struct HexId(pub u32);                     // 0-based index = old id − 1
pub struct GridSpec { cols: u16, rows: u16, origin_lon: f64, origin_lat: f64, w: f64, h: f64 }
impl GridSpec {
    fn col_row(&self, id: HexId) -> (u16, u16);
    fn polygon(&self, id: HexId) -> [LonLat; 6];
    fn neighbours(&self, id: HexId) -> impl Iterator<Item = HexId>;   // even-q/odd-q offsets
    fn hex_at(&self, p: LonLat) -> Option<HexId>;                     // hit test
}

#[repr(u8)] pub enum Terrain { Water, Ice, Plains, Mountains, Land, Chaparral, ExtremeDesert,
    SemiDesert, Free, Savannah, Woodlands, TropicalForest, Grassland, TemperateForest,
    SteppeForest, BorealForest, Unknown, Tundra, Alpine } // Land + Unknown explicit (fixes D14);
                                                // Mountains kept only so old files load
#[repr(u8)] pub enum Landform { Flat, Hills, Mountains, HighMountains } // static, per hex
pub struct Koeppen(u8);                         // 0..=30; .code() -> "Cfb" (replaces `climate`)
#[repr(u8)] pub enum PopDensity { P0_0, P0_1, P0_3, P0_5, P0_8, P1_0, P1_5, P2_0, P5_0 } // ordered (fixes D15)

/// A step function over keyframes. Sorted by year; value holds until the next key.
pub struct Timeline<T> { keys: SmallVec<[(Year, T); 8]> }
impl<T: Copy> Timeline<T> { fn at(&self, y: Year) -> Option<T>; fn set_key(&mut self, y: Year, v: T); }

pub struct World {
    pub grid: GridSpec,
    pub terrain: Vec<Timeline<Terrain>>,        // indexed by HexId (struct-of-arrays)
    pub koeppen: Vec<Timeline<Koeppen>>,
    pub pop: Vec<Timeline<PopDensity>>,
    pub settlements: Vec<Settlement>,
}

pub struct Settlement { id: u32, name: String, pos: LonLat, founded: Year, population: Timeline<u32> }
```

**Derived state.** `World::snapshot(year) -> Snapshot` is three flat `Vec<u8>` arrays, one per property. It costs 26k × 3 timeline lookups, well under 1 ms. That makes a precomputed change log (the server's `prepare_hex_updates`) unnecessary. The clock asks for the snapshot only when the year crosses a keyframe (`World::keyframe_years()`), and that also makes **scrubbing backwards** work for free.

**Typed values everywhere.** The palette yields a `Terrain`, `Koeppen` or `PopDensity`, never a string, so D8 can't happen.

## 6. Editing model

Today an edit changes the *flattened current value* in the browser and is lost on reload (D11). With time-keyed data, an edit has to say **which keyframe** it changes.

**Rule (recommended):** an edit changes the keyframe *in effect* at the current year. At −7500 that's the −8000 key. A toolbar toggle, **"Insert keyframe at current year"**, creates a new key instead. That's how the Doggerland drowning sequence could be authored at a finer time resolution.

```rust
pub enum Prop { Terrain, Koeppen, Pop }
pub enum Value { Terrain(Terrain), Koeppen(Koeppen), Pop(PopDensity) }

pub struct Edit { hex: HexId, prop: Prop, key: Year, before: Option<Value>, after: Value }
pub struct Command { label: &'static str, edits: Vec<Edit> }  // one stroke / one fill = one command

pub struct History { undo: Vec<Command>, redo: Vec<Command> } // apply/revert are exact inverses
```

Tools are pure functions in `core` that **return a `Command`**. They don't touch the world directly, so they're easy to test:

- `pencil(world, sel, prop, value, year)`: the clicked hex. A drag gathers every hex it passes over into one command.
- `fill(world, start, prop, value, year)`: BFS with a `visited` bitset over `grid.neighbours`. It returns an empty command if the value already matches, which fixes D7.
- `lasso(grid, polygon) -> Selection`: point-in-polygon test on hex centres.
- `Selection` (a bitset): select all, deselect all, and pencil-paint the selection.

**Persistence:** `world.bin` (postcard plus zstd, versioned header). Native builds use a file open/save dialog (`rfd`). Web builds download the file and use `<input type=file>` for upload, which replaces the dead Upload/Download buttons (D13). `convert --to-geojson` turns `world.bin` back into the `combined_map.geojson` format for the Python tools.

## 7. App (`crates/app`)

### 7.1 Screens and layout (egui)

- **Start screen:** title, start year (a `DragValue` with a BCE/CE label) and Start.
- **Main:**
  - `CentralPanel`: the board view (§7.2), with a Curved ↔ Flat toggle in its corner.
  - Top bar: map-mode selector (Terrain, Köppen, Population), Game/Editor toggle, file menu.
  - Bottom bar: timeline. Play/Pause, speed (1 to 500 years/s, logarithmic), a year **scrubber** with tick marks at keyframes, and the year readout.
  - Right `SidePanel`: an inspector for the hovered or selected hex. It shows the current values plus each property's keyframe table, editable in place with typed dropdowns (this replaces the raw JSON editor). A collapsible "raw JSON" view stays available for debugging.
  - Left `SidePanel` (editor mode only): tools, a palette for the current mode with labelled swatches (not just colours), undo/redo, and a "keyframe in effect" indicator.
  - Settlement popup on click: name, founding year, and population at the current year.

The fields with no data behind them (resources, agriculture, trade, calories; D19) are **dropped** until the simulation provides them.

### 7.2 Board rendering (`app::board`)

**The look.** An idealized tabletop piece: one solid, curved tile of the planet resting in a neutral studio space. It has crisp hex tiles separated by thin grout lines, a visible thickness with a hex-stepped edge, soft lighting and a soft contact shadow. It's made to read like a board-game board, not like a satellite globe. Nothing is drawn outside the grid, so there's no rest-of-Earth, no atmosphere and no stars.

**Pipeline.** The board is drawn with wgpu into an **offscreen colour + depth target**, inside the `prepare` step of an `egui_wgpu` paint callback. The result is shown in the `CentralPanel` as an egui texture. The board has side walls and an underside, and isn't convex when seen from low angles, so it needs a real depth buffer. Owning the depth buffer avoids relying on egui's render pass. Drawing directly with wgpu rules out eframe's `glow` backend. On the web, wgpu uses WebGPU where available and otherwise WebGL2.

#### 7.2.1 Geometry (built once at load)

- **Placement:** the board's top surface is on the unit sphere. The scene is rotated so the board's centre (about 41°N, 25°E) sits at the top (+Y). The board then rests "on the table", and orbit, tilt and lighting are all relative to its centre.
- **Top surface (tiles):** each hex is a triangle fan of a centre vertex and 6 rim vertices, making 6 triangles. Over 26,410 hexes that's about 185k vertices and 158k triangles, all in one static vertex buffer:

  ```rust
  #[repr(C)] struct HexVertex {
      sphere: [f32; 3],   // unit-sphere position: (cosφ·cosλ, sinφ, −cosφ·sinλ), then board-rotated
      flat:   [f32; 2],   // equirectangular (λ, φ) in radians, for the curved ↔ flat morph
      cell:   [u16; 2],   // (col, row) → texel in the state texture
      edge:   u8,         // which of the 6 edges this fan triangle sits against (0..6)
      rim:    u8,         // 0 at the centre vertex, 255 on the rim → interpolated distance to edge
  }
  ```
- **Edge walls:** for every hex edge on the outside of the grid (an edge with no neighbour), make a quad from radius 1.0 down to radius `1 − d`, with `d ≈ 0.015` (the board's thickness). The edge follows the hex outline, so the sides are **stepped like a hex-tile board**, not cut flat. These are generated in `core` from `GridSpec` (outside edges are the ones where `neighbours` comes back empty) and number about 2k quads.
- **Underside:** the same fan triangles at radius `1 − d` with their winding reversed, in one flat colour. It's only visible at extreme angles, but it makes the board solid.
- **Board frame (optional, an aesthetic call):** a thin raised lip just inside the outer edge, like the printed border on a physical board. It's a toggle so the plain tile edge can be compared against it.

#### 7.2.2 Studio scene

- **Background:** a soft vertical gradient (warm grey to darker grey), drawn as a fullscreen triangle. It works in light and dark UI themes.
- **Contact shadow:** a quad under the board with a blurred elliptical falloff baked into its shader. It's cheap, needs no shadow maps and anchors the board in space.
- **Lighting:** a key light from above-front-left plus a dim fill light and ambient. Lambert shading on the curved surface makes the curvature visible. Edge walls catch the light differently from the top, which defines the silhouette. A "flat lighting" toggle is available for editing where colours need to be exact.

#### 7.2.3 Colour without re-uploading geometry

- **State texture:** a 190 × 139 `R8Uint` texture *per property*, indexed by `(col, row)` and holding the enum value from the current `Snapshot`. Because the grid is rectangular, a 2D texture works as the lookup table, which keeps it WebGL2-compatible since storage buffers aren't needed.
- **Palette texture:** a 256 × 4 `Rgba8` texture with one row per map mode (terrain, Köppen, population, elevation).
- **Elevation:** a static per-hex median (`World::elevation`, `world.bin` version 4) shown as a read-only map mode. The snapshot turns it into a band byte (depth bands for hexes that are Water that year, height bands otherwise) and uploads it to a separate texture (now `Rg8Uint`, band plus hillshade), because the state texture's alpha channel holds the selection flags. Borders between bands act as contour lines.
- **Landform:** a static per-hex `Option<Landform>` (`World::landform`, `world.bin` version 5), separate from the biome in `terrain`. It rides in bits 3–4 of the state texel's flags byte (`scene::LANDFORM_SHIFT`). Mountain hexes draw peaks and foothills over their biome colour, and hills hexes draw two hill glyphs among the biome's own. Files without landform fall back to drawing peaks on the old `Mountains` terrain.
- **Relief layer:** independent of the map mode (a top-bar toggle, exaggeration in Board style, `--relief <x>` for screenshots). `World::surface_heights` gives each hex a surface height per year: land at `max(elevation, 0)`, Water inside a lake shoreline (or next to a hex that is) at the lake's level, other Water at `max(elevation, 0)`, so the sea is at 0. It goes to an `R16Sint` height texture, and the vertex shader raises tile tops, the outside walls' top edges and the 3D terrain art by `height × relief scale`, where one board unit is Earth's radius. **Steps:** the mesh has one quad per inside edge (`KIND_STEP`, built on each hex's NE, N and NW edges), running from the hex's top to its neighbour's. It is double-sided (both windings over the same 4 vertices), so whichever side is lower sees the cliff face. The vertex shader colours it by the higher hex (every vertex picks the same cell, so the flat `cell` doesn't depend on provoking-vertex rules), in that tile's colour at 62%. Steps add about 80k quads (~320k vertices) to the board's ~370k; GPU buffers total about 27 MB. On the CPU, `board::relief::Relief` mirrors the lift for picking (`View::pick_relief` steps down through the height range to the first tile the ray is under), settlement pieces, and river and lake ribbons (each point at the highest tile among it and its neighbours, so lines stay on top of steps).
- **Hillshade:** `elevation::hillshade` fits a plane through each hex and its neighbours (least squares, 30× vertical exaggeration) and lights it from the north-west at 45°. The result is one static byte per hex, computed when a world loads, stored in the relief texture's green channel (128 = level ground). The shader multiplies land tiles by it in every map mode, scaled by the style's Hillshade slider (`lines.y`; `--hillshade` on the command line). Hexes that are Water that year aren't shaded.
- **Fragment shader:** `colour = palette[mode][ state[mode][cell] ]`. Changing epoch rewrites one 26 KB texture. Changing map mode updates one uniform. Editing a hex writes a single texel.
- **Borders in the shader:** `edge` gives the neighbouring cell, using the same even-q/odd-q offsets as `GridSpec::neighbours`. If that neighbour's value differs and `rim` is close to 1, the fragment is darkened. This gives Paradox-style region borders at no CPU cost, and they update instantly when you paint. A faint full hex grid fades in as you zoom in (its strength comes from the camera distance).
- **Selection, hover and lasso** use a fourth `R8` texture of flags (selected, hovered, in lasso) that tints and outlines those hexes in the same shader.
- **Tile treatment (the "idealized" part, all shader-only):**
  - A thin **grout line** at `rim > 0.94` in a darker version of the board colour, so each hex reads as a separate tile.
  - A slight **bevel**: the normal is tipped outward near the rim, so tiles catch light on their edges.
  - Mild colour quantization and saturation control, so palettes look printed rather than photographic.

  All three fade out when zoomed far out (too fine to show) and are adjustable from a "board style" panel while tuning the look.
- The **edge walls and underside** use a fixed material (e.g. a warm wood or slate colour, set by a uniform). They don't depend on the map mode.

#### 7.2.4 Curved ↔ flat morph

The vertex shader blends the two positions:

`pos = mix(sphere, plane(flat), t)`

`plane(flat)` puts the equirectangular coordinates on the plane tangent to the board's centre. Edge walls and the underside morph along with the top. `t` animates over about 400 ms when the toggle is pressed, and can also be set from a **curvature slider** while tuning the look. The flat board keeps the precise, distortion-free layout for detailed painting. The curved board is the default view.

#### 7.2.5 Camera and picking

- **Orbit camera around the board's centre**, kept so the board always stays in view, like looking at a model on a table:
  - **Yaw:** free, so you can walk around the table.
  - **Pitch:** from about 15° above the board's surface (looking across it, with the far edge dropping away over the curvature) to 90° (straight down).
  - **Zoom:** distance clamped from "a few hexes fill the screen" to "the whole board plus margin".
  - **Pan:** the look-at point stays inside the board's lon/lat bounds.
- **Controls:**
  - Left-drag *grabs the board*, so the point under the cursor stays under it (rotating the look-at point along the sphere using the start and end ray hits).
  - Right-drag or Ctrl-drag orbits and tilts.
  - Wheel or pinch zooms toward the cursor.
  - Light inertia when you release the drag.
  - Double-click glides to a hex.
  - The starting view is three-quarters from the south at about 50° pitch, with the whole board in frame.
- **Picking is analytic, with no GPU readback:** cast a ray through the cursor, intersect it with the unit sphere (a quadratic with the nearer root), convert the hit point to lon/lat, and call `GridSpec::hex_at`. A miss or a point outside the grid means nothing is under the cursor. In flat mode the ray hits the tangent plane instead. It's O(1) and the same on web and native. Edge walls can't be picked.
- **Lasso:** project hex centres to screen space, then run point-in-polygon against the screen-space lasso path. At extreme tilts, hexes hidden by the curvature are excluded by checking that the screen-to-sphere ray hits that hex first.
- **Settlement pieces:** settlements are shown as small **3D game pieces** standing on their hex. A stylized marker (e.g. a hut or obelisk mesh, sized by population tier) is instanced in the same pass and lit like the board. Name labels are drawn by egui as an overlay at the projected position and hidden when far zoomed out. Clicking a piece takes priority over clicking the hex underneath.

### 7.3 Clock

A fixed-step accumulator in `update()`:

```rust
if playing { acc += dt * years_per_sec; while acc >= 1.0 { year += 1; acc -= 1.0; } }
if year crossed a keyframe or the user scrubbed { snapshot = world.snapshot(year); }
```

There's one code path for play, pause, speed and scrub, so D1, D5 and D6 can't happen. Entering editor mode pauses the clock, and the JSON editor no longer exists (D9).

### 7.4 Colours

Palettes are `const` tables in `app`, keyed by the typed enums, so a colour can never be assigned implicitly by the scale. The Köppen palette is copied from `settings.COLOR_SCHEMES`. Terrain adds colours for `Land` and `Unknown`. The population palette is a perceptual ramp in order (viridis-like, or the existing greyscale with its order fixed).

## 8. Data conversion (`crates/convert`)

`neolith-convert combined_map.geojson settlements.geojson -o assets/world.bin` does the following:
1. Derives `GridSpec` from the `left/top/right/bottom` fields and checks every hex lands on an integer `(col, row)` (fails loudly otherwise).
2. Parses property strings into enums, reporting unknowns with their counts.
3. Checks that `climate == koeppen.code()` for every hex-epoch and warns on any mismatch.
4. Reads settlements as a bare array (accepting the current non-GeoJSON shape, D17), dedupes ids 7/8 with a warning, and stores years as `Year`.
5. Writes a versioned postcard + zstd file.

It also has `--to-geojson` for the round trip, and `--stats` for an epoch-by-epoch summary of the data (it would flag the placeholder −10000/−4000/−3000 epochs, D16).

## 9. Hosting

- **Web:** `trunk build --release` produces static `index.html` + `.wasm` + `world.bin`. wgpu uses WebGPU where available and falls back to WebGL2. The shader code sticks to features that work on WebGL2: textures only (no storage buffers), and `textureLoad` for the integer state lookups. It can be served from anywhere (S3/CloudFront, Vercel, GitHub Pages) or, during the transition, from Django's `/static/`. With no server state, the LocMemCache, multi-worker, CSRF and deploy-config problems go away entirely (D20–D24).
- **Native:** `cargo run -p neolith-app` loads `assets/world.bin`, with native file dialogs for open and save.
- Django can be retired once the Rust app is at parity. Nothing in the backend is needed after conversion.

## 11. Open questions

1. **Edit semantics:** is "edit the keyframe in effect, optionally insert a keyframe" the right model, or should edits always create a key at the current year?
2. **Grid geometry:** the curved board shows plainly that lon/lat hexes shrink toward the pole, to about a quarter of their width at 75°N. Keep this grid (no data changes), or later re-sample onto an equal-area geodesic grid (e.g. H3 or an icosahedral grid)? That would change the editor's tools and the adjacency math but not the rendering design. A re-sampled grid would no longer be a rectangle, so the state lookup would become a 1D texture indexed by hex id.
3. **Board style:** wood, slate or printed-cardboard edges? A raised frame lip or a plain edge? These are cheap to compare once M2a renders, so the board-style panel exists to make the choice with screenshots rather than up front.
4. **Curvature:** true curvature (this patch covers about 70° of arc, so it's clearly curved), or an exaggeration slider that goes past true? Going past true needs a smaller sphere radius for the board, which is easy, but then it's no longer "true".
5. **Keep the Python pipeline?** If the Rust editor becomes the authoring tool, `world.bin` becomes the source of truth and the GeoJSON becomes an export.
6. **Unused datasets:** should DNA samples (point layer) and cultures arrive as part of the UI rebuild, or wait for the simulation crate?
